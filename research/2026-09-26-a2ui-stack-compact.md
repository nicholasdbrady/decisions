# JEV through MAF, AG-UI, CopilotKit, and A2UI

**Direct answer:** The stack is feasible, and it can remove the bespoke React card renderer and custom transport. It is not a drop-in combination in this checkout: MAF A2UI is optional and the current Python lock is below its current core dependency floor; CopilotKit's documented A2UI APIs and examples use versions that do not match JEV's `2.0.0-next.1` packages. No primary source provides an end-to-end latency comparison for a JEV-selected surface versus Luna-authored A2UI.

**Recommended pattern:** Let JEV return closed-set choices and state signals. Use those decisions to select approved A2UI catalog components and let a small deterministic server-side assembler emit A2UI messages. Keep that assembly declarative and spec-conformant; do not ask JEV to write JSON trees. Use Luna for semantic fields, web/code lanes, and other work that needs generation. Return tool results as A2UI operations through MAF's demonstrated tool path, then let CopilotKit's A2UI middleware and renderer handle the stream. Start with the standard catalog. Add a custom catalog only if a required interaction cannot be composed from standard components.

The pattern fits JEV's typed `Choice`, `Score`, and `Noul` decisions and CopilotKit's first-party JEV recipe, where the app owns components and JEV selects among prepared choices. TypeSafe says it evaluates batched questions in parallel; that is not a guarantee of end-to-end time-to-surface. Measure the actual integration before claiming a typing-speed result. ## What is verified

- **A2UI:** The official project identifies v0.9.1 as the current production release and v1.0 as a release candidate. The v0.9 message set is `createSurface`, `updateComponents`, `updateDataModel`, and `deleteSurface`. A2UI separates component structure from data, supports JSON Pointer bindings and user actions, and streams JSON messages. [A2UI version index](https://github.com/a2ui-project/a2ui/blob/ec12ba915ab21725929430bd14bcef04e5ee7f12/docs/public/index.md) · [Overview](https://github.com/a2ui-project/a2ui/blob/ec12ba915ab21725929430bd14bcef04e5ee7f12/docs/public/concepts/overview.md)
- **Catalog limits:** The Basic Catalog has general layout, text/image/icon, form, and container components. It does not document native dice, wheel, blackjack, or color-palette widgets. Those experiences can be approximated with standard lists, text, inputs, and buttons, but keeping their current rich, stateful behavior likely needs a custom A2UI catalog and a matching client renderer. This is an inference from the catalog inventory, not a protocol restriction. [Component Gallery](https://github.com/a2ui-project/a2ui/blob/ec12ba915ab21725929430bd14bcef04e5ee7f12/docs/public/reference/components.md) · [Catalogs](https://github.com/a2ui-project/a2ui/blob/ec12ba915ab21725929430bd14bcef04e5ee7f12/docs/public/concepts/catalogs.md)
- **CopilotKit:** Current source exports A2UI renderer/theme APIs from `@copilotkit/react-core/v2`; `@copilotkit/a2ui-renderer` provides `createCatalog(definitions, renderers, options?)`. Official examples use a Next.js App Router and React 19. However, the maintained A2UI example pins CopilotKit 1.73.2 and uses an A2UI 0.8 Lit renderer; current source manifests are 1.74.0 and refer to A2UI 0.9. Neither proves compatibility with JEV's locked `2.0.0-next.1` channel. [CopilotKit v2 exports](https://github.com/CopilotKit/CopilotKit/blob/e8d096b94352286f2a312f349a3b1c18778c01f4/packages/react-core/src/v2/index.ts) · [Renderer catalog API](https://github.com/CopilotKit/CopilotKit/blob/e8d096b94352286f2a312f349a3b1c18778c01f4/packages/a2ui-renderer/src/web-components/create-catalog.ts) · [Maintained example](https://github.com/CopilotKit/CopilotKit/tree/e8d096b94352286f2a312f349a3b1c18778c01f4/examples/integrations/a2a-a2ui)
- **MAF:** Current `agent-framework-ag-ui` 1.4.0 offers an optional `a2ui` extra and official fixed-schema examples that return `a2ui_operations` from tools. The same sources show dynamic `render_a2ui` argument streaming, but warn that a Responses/Azure fallback may not progressively paint. A2UI via AG-UI snapshots or custom/activity events was not demonstrated. JEV locks 1.3.0 and `agent-framework-core` 1.18.0; the current A2UI package metadata requires core >=1.19.0,<2. [MAF A2UI example](https://github.com/microsoft/agent-framework/blob/6f1522a50b66f117da34cc25ea299ba24a528b15/python/packages/ag-ui/agent_framework_ag_ui_examples/agents/a2ui_agents.py) · [MAF package metadata](https://github.com/microsoft/agent-framework/blob/6f1522a50b66f117da34cc25ea299ba24a528b15/python/packages/ag-ui/pyproject.toml)

## JEV and Luna

JEV is a typed decision engine, not a free-form A2UI author. OpenRouter Decisions uses `state` plus named typed questions; TypeSafe's SDK exposes `Choice`, `Score`, `Noul`, and `systemOne()`. Do not conflate the TypeSafe SDK endpoint with OpenRouter's separate Decisions endpoint. The 250 ms in JEV's current frontend is a debounce before `/api/classify`, not a measured model response time. [OpenRouter Decisions API](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request) · [TypeSafe SDK questions](https://github.com/typesafe-ai/typesafe-sdk-js/blob/66880ccded6cb642dc1809620c2b108c33730214/src/questions.ts) · Local: `frontend/src/hooks/use-jev-classification.ts:25-69`

**Comparison:** selecting a whole predefined surface is simplest but can overconstrain layout; per-slot closed-set JEV questions plus deterministic assembly are the best fit; Luna-authored A2UI is a plausible optional path for open-ended layouts but adds a generation step and has no relevant latency result; a hybrid can show an immediate skeleton, then apply JEV's choice and Luna's extracted data. The recommendation for JEV plus deterministic assembly follows typed-model limits and the first-party cookbook, not a measured latency win. ## Codebase mapping

**Keep and adapt:** `backend/src/backend/jev.py` for closed-set decisions; `extract.py` and `luna.py` for strict Luna fields and web/Python lanes; `compute.py`, `providers.py`, and `units.py` for deterministic calculations and data; `telemetry.py` for existing OpenTelemetry/Foundry tracing; `frontend/src/lib/history.ts` if local history remains in scope.

**Convert:** turn JEV, Luna extraction, shopping expansion, unit conversion, weather/currency/holiday resolution, and user-triggered recomputation into MAF tools. Feed their results into the A2UI data model. Preserve the existing staleness/cancellation rules when moving request ownership.

**Replace or remove after parity:** bespoke `CardWidget` branches in `command-canvas.tsx`, plus `random-widget.tsx`, `poll-widget.tsx`, and `password-widget.tsx`; their view structure becomes A2UI messages and standard-catalog components. Keep the omnibar shell, menu, keyboard flow, Inspector, history, and timer/game state only if redesigned with standard components. The `/api/copilotkit` proxy and `HttpAgent` are already present; remove the private nested AG-UI client import after package alignment. Move direct frontend calls to `/api/classify`, `/api/decide`, `/api/extract`, `/api/judge`, `/api/expand`, `/api/convert`, and `/api/units` behind the MAF/AG-UI flow rather than adding another transport.

The source contains 21 schema IDs and 21 `CARD_TYPES`; README says 15 and DESIGN says 19 in one menu sentence. Resolve this documentation drift as part of the migration scope. ## Smallest proof and unresolved gaps

Build one temperature-conversion surface from standard `TextField`, `ChoicePicker`, and `Text` components. Have JEV select the surface, the MAF tool call existing deterministic `compute()`/Pint logic, and the A2UI data model update through the existing Next.js CopilotKit proxy. Verify one unit-change action returns through AG-UI and one OpenTelemetry trace spans the operation. In the same bounded proof, compare a prepared JEV-selected surface with an equivalent Luna-authored A2UI surface, recording time to first usable render and action success. Do not call the result a typing-speed win until measured.
