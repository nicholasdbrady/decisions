Recommended pattern

Back to top

Use closed-set JEV decisions to choose approved A2UI components, then assemble A2UI messages deterministically in the Python agent. Have MAF tools return A2UI operations through the demonstrated tool-result path. CopilotKit's A2UI middleware and renderer consume that stream and send user actions back through AG-UI. Keep Luna on semantic field extraction and optional web/Python work; do not make it author the first UI frame.

This is a conditional design recommendation, not a measured speed winner. JEV's typed questions fit bounded selection, and the first-party CopilotKit Jev recipe uses prepared controls with app-owned components and validation. TypeSafe describes parallel batched decisions but publishes no relevant time-to-render guarantee. A bounded proof must measure this repository's first usable A2UI frame and action round-trip before the team claims typing-speed performance. TypeSafe Introduction · CopilotKit Jev generative UI

Requirement boundary: “No custom transport” is achievable with the standard AG-UI/CopilotKit route. “No custom or bespoke UI” is achievable only if JEV accepts generic standard-catalog compositions or reduced interactions. To preserve the current animated dice/wheel, blackjack, and palette behavior, A2UI custom-catalog components plus client renderers may still be needed. That is an A2UI extension, not a custom transport.

The diagram is a target design, not a claim that the current checkout already emits A2UI. Existing code has an AG-UI transport acknowledgement only.

Research frame

Back to top

Question: how to rebuild the JEV omnibar so JEV chooses the visible interaction from app state and the UI travels through Microsoft Agent Framework (Python), AG-UI, CopilotKit, and A2UI, without hand-built card widgets or custom transport.

Primary route: implementation patterns. Secondary route: codebase architecture. Depth: extensive, because the answer spans fast-changing protocols, package versions, cross-vendor integration, and a material migration decision.

Assumptions: this remains an ambitious local demo; do not add deployment/auth setup or paid services. Existing Foundry, OpenRouter, and provider configuration can be reused. Keep current semantic intent where practical, but state clearly where a standard A2UI catalog cannot reproduce a bespoke interaction.

A2UI protocol and catalog

Back to top

Version status

The official A2UI project index marks v0.9.1 as the current production release; v0.9 is the previous stable protocol family and v1.0 is a release candidate. The project README corroborates that status. The exact GitHub release/tag history was not independently inspected, so this report uses the official current status index and README rather than claiming a release-tag audit. [A1][A2]

Lifecycle and interaction

For v0.9, the documented server-to-client operations are createSurface, updateComponents, updateDataModel, and deleteSurface. The overview describes streamed JSON messages, one object per JSONL line. A2UI keeps component structure separate from a surface data model; JSON Pointer bindings update components reactively, and template-driven lists can represent repeated data. [A3][A4]

The component action guide distinguishes local renderer functions from events dispatched to the agent. The overview describes user actions returning to the agent and updated A2UI messages coming back. The v1.0 candidate adds an actionResponse operation; do not assume that candidate RPC behavior is the production v0.9 wire contract. [A3][A5]

Standard components and the no-bespoke limit

The documented Basic Catalog includes Row, Column, List, Text, Image, Icon, Divider, Button, TextField, CheckBox, Slider, DateTimeInput, ChoicePicker, Card, Modal, and Tabs. Catalogs declare what components/functions an agent may reference; renderers validate against a versioned catalog. A custom catalog still needs matching renderer implementations. [A6][A7]

Inference from the documented inventory: a standard list can display weather periods; standard buttons and data bindings can express simple poll choices or game commands; a color value can be shown as text or an image. The standard catalog does not document a native color wheel, animated dice, wheel pointer, blackjack table/game rules, or local game interactions. Generic standard components can approximate these experiences but do not preserve their current interaction quality. Keeping those behaviors requires an A2UI custom catalog/client component, or an explicit decision to simplify/defer them.

Scope decision: The protocol path itself does not require a bespoke transport. It does require the app to build or generate valid A2UI operations, define its permitted catalog, and validate user actions. That is declarative A2UI integration work, not a custom wire protocol.

CopilotKit renderer and version skew

Back to top

Verified API surface

Current CopilotKit source exports createA2UIMessageRenderer, A2UITheme, and a2uiDefaultTheme from @copilotkit/react-core/v2. The @copilotkit/a2ui-renderer package provides createCatalog(definitions, renderers, options?); its options include a catalog ID and includeBasicCatalog. The v2 provider examples register a catalog or theme under a2ui. [C1][C2]

A maintained CopilotKit A2UI example contains Next.js App Router files and uses React 19 with @copilotkit/react-core/v2. Its package manifest pins CopilotKit packages at 1.73.2, Next at 16.0.10, and React at 19.2.3. That example uses @a2ui/lit 0.8 and a custom v0.8 renderer; it proves framework integration, not a one-to-one v0.9 renderer recipe. Current CopilotKit source manifests report 1.74.0, support React 19, and the renderer source uses A2UI 0.9. [C3][C4]

Compatibility judgment

Not verified for the current repo lock. The JEV app currently resolves @copilotkit/react-core and @copilotkit/runtime to 2.0.0-next.1, whereas the current official source manifests and maintained A2UI example use package versions 1.74.0 and 1.73.2 respectively, with a /v2 API subpath. Do not treat a /v2 import as proof that the separate 2.0.0-next.1 package has the same A2UI APIs. The exact prerelease dist-tag/API parity was not verified. [C1][C3][C4]

The official transport pattern is a same-origin CopilotKit runtime route, with a server-side HttpAgent connecting to the AG-UI backend and A2UI middleware enabled. This matches the current JEV route shape. JEV's current copilotkit-http-agent.ts reaches into CopilotKit's private nested AG-UI client to avoid a dependency-contract mismatch; that brittle import should be removed by aligning supported versions, not expanded into another transport. [C5][C6]; local: frontend/src/app/api/copilotkit/route.ts:1-25, frontend/src/lib/copilotkit-http-agent.ts:1.

Version gate before migration: select a version combination that explicitly supports the A2UI protocol version and run one end-to-end stream/action proof. The evidence shows plausible APIs and examples, but no exact published matrix covering JEV's CopilotKit next channel, AG-UI JS canary, MAF 1.3 lock, and A2UI 0.9.1.

MAF, AG-UI, and A2UI output

Back to top

The current Microsoft Python package has optional A2UI support under the a2ui extra. Its current package metadata reports agent-framework-ag-ui 1.4.0 and requires agent-framework-core >=1.19.0,<2. JEV currently locks AG-UI 1.3.0/core 1.18.0 and declares no A2UI extra; changing this means aligning these dependency versions and installing the extra together. [M1][M2]; local: backend/pyproject.toml:10-11, backend/uv.lock:18-47.

Demonstrated A2UI paths

  • Fixed-schema tool result: official MAF examples show ordinary backend tools returning an a2ui_operations JSON-string envelope. The A2UI runtime middleware detects that envelope and emits the operations through the agent interaction path. This is the best fit for a deterministic assembly step after JEV picks a schema and slot decisions. [M2]
  • Generated surface: examples use a render_a2ui tool whose arguments can stream progressively. Sample comments prefer a Chat Completions client for progressive paint and warn that the Responses/Azure fallback may not paint incrementally. This makes free-form model-authored layouts a poor assumption for the current raw Responses-based Luna client. [M2]
  • State snapshots/custom events: MAF supports state snapshots and emits custom events for other workflow/approval purposes, but inspected official A2UI samples do not show A2UI operations in those snapshots, custom events, or activity messages. Treat them as unverified A2UI paths rather than equivalent to the tool-based example. [M4][M5]

The AG-UI Dojo Python integration registers the Microsoft A2UI example endpoints, although its README feature list lags the code. This corroborates the existence of examples but does not prove a Next.js CopilotKit runtime proxy recommendation; the CopilotKit runtime-side HttpAgent example is the better match for this app. [M3][C5]

Tools and data updates

MAF tools should own operations, not custom widget rendering. Keep the existing strict Luna extraction schema as an enrichment tool; use existing compute/provider services for values that must be deterministic. After a tool returns, emit/update A2UI's data model so bound text, lists, and controls redraw. For user-driven recomputation, send the standard A2UI action through the CopilotKit/AG-UI path, call the relevant MAF tool, and send a data-model update back. Use the demonstrated fixed-tool envelope for the first slice; adopt the generated render_a2ui tool only if open-ended layout authoring is a validated need.

Keep the existing Foundry/OpenTelemetry instrumentation. The current app configures OpenTelemetry, instrumented FastAPI/httpx, Agent Framework spans, and Foundry/Application Insights export. Preserve tool spans, usage, and the current sensitive-data settings; do not add payload logging to compensate for a new stream. Local: backend/src/backend/telemetry.py:43-120,158-288.

JEV's role and Luna's role

Back to top

TypeSafe documents JEV as a System One model: software supplies state and typed questions, and gets typed answers and distributions. Choice, Score, and Noul can be mixed and evaluated in parallel in one API call. The SDK's systemOne() shape and OpenRouter's Decisions API are separate transports; JEV's existing Python adapter uses OpenRouter's state/questions shape. [J1][J2][J3]

This makes JEV a good selector for schema, layout slot, and semantic state signals. It does not make JEV a free-form A2UI JSON generator. The previous audit likewise advises keeping math/date precision in code and using a generative model for generation or segmentation that JEV does not handle well. [J4][J5]; local: backend/src/backend/jev.py:25-131,221-318,388-456.

The frontend's 250 ms is a debounce before the direct /api/classify fetch, not the model's response latency. The classify call measures and returns latency, but neither local code nor the retrieved official docs establish time from user typing to a ready A2UI surface. CopilotKit's first-party Jev recipe has the app own prepared controls and validation; JEV selects the panel and scores candidates, while an optional generative model handles requests outside the prepared choices. [J1][J5]; local: frontend/src/hooks/use-jev-classification.ts:25-69, frontend/src/lib/classification-client.ts:10-27.

Candidate choice: use bounded JEV decisions to choose permitted A2UI slots/components and deterministic assembly to serialize the surface. Keep Luna on strict field extraction and optional web/Python work. Consider a local A2UI skeleton while JEV runs if initial paint needs to precede the decision. Use Luna-authored A2UI only as an optional fallback for layouts outside the approved composition space, and validate it against the selected catalog. This is a design choice supported by the typed API and cookbook pattern; no comparative timing result was found.

Latency evidence: TypeSafe's official docs say adding batched questions barely changes response time, but publish no relevant end-to-end benchmark. CopilotKit's recipe documents pattern, not timings. No primary source reports apples-to-apples time-to-first-usable-surface or action success for JEV-selected versus Luna-authored A2UI. Numeric claims from unverified or secondary pages were excluded. [J1][J5]

Phased migration and smallest proof slice

Back to top
  1. Pin a supported version set. Align agent-framework-ag-ui[a2ui] with a core version in its required range; pick CopilotKit runtime/renderer packages and an A2UI protocol/catalog version explicitly; verify React 19, Next App Router, the CopilotKit /v2 API, and the existing remote-agent bridge. Remove the private nested AG-UI import only after the replacement is validated. Do not assume JEV's current preview lock works.
  2. Prove one standard-catalog interaction. Implement a temperature-conversion A2UI surface with standard TextField, ChoicePicker, and Text. JEV selects the conversion surface; a MAF tool calls the existing Pint-backed compute; the response updates the bound A2UI data model. Change one unit through an A2UI user action and verify the result returns through AG-UI/CopilotKit. Use the already available Foundry/OpenRouter setup only; add no new paid service.
  3. Compare the two authoring paths on the same slice. In the bounded proof, render the same allowed surface through (a) JEV choice + deterministic assembly and (b) Luna schema-constrained A2UI authoring. Record request start, first valid A2UI operation, first usable render, final render, and action success. Do not compare different surfaces or claim an SLA from a single run. Capture enough repeats to see variability, then decide whether Luna authoring has a place outside fallback.
  4. Wire current services to data updates. Add MAF tools for strict Luna extraction, deterministic compute/providers, weather/currency/holidays, and shopping expansion. Keep structured tool errors visible. Update A2UI data bindings from validated results; preserve stale-input guards and telemetry attributes.
  5. Replace surfaces by capability, not by card count. Migrate plain text/list/form surfaces first. For each rich card, decide either to compose with standard catalog components, simplify/defer its behavior, or add the smallest versioned A2UI custom catalog component. Do not rebuild the current React widgets behind A2UI as hidden bespoke controls.
  6. Retire direct REST client paths and validate parity. Move user-initiated paths behind MAF/AG-UI. Test accessibility, keyboard flow, stale responses, tool errors, action round-trips, metrics/traces, and package-lock repeatability before deleting the old rendering/API paths.
Smallest first proof: one standard-catalog temperature converter, one JEV selection, one deterministic Python computation, one user action/data update, one Foundry/OTel trace, plus a matched Luna-authored variant for measurement. This tests the highest-risk version, renderer, transport, and latency assumptions without migrating all 21 cards.

Supporting and adversarial evidence

Back to top

Evidence supporting the recommendation

  • A2UI defines the component, data, and action protocol needed for data-bound generated surfaces; custom catalogs are an explicit, versioned extension point. [A3][A4][A5][A7]
  • CopilotKit provides an A2UI renderer, theme/catalog APIs, and an App Router/React 19 example. Its official Jev cookbook uses bounded choices and app-owned components, which aligns with JEV's closed-set output. [C1][C2][C3][J5]
  • MAF's optional Python A2UI toolkit and official examples demonstrate both fixed tool-result operations and a generated rendering tool; a current MAF AG-UI endpoint already exists in JEV. [M1][M2]; local: backend/src/backend/main.py:4,62-68.
  • JEV already classifies schemas and state signals in one Decisions request; Luna extraction, deterministic compute/providers, and OpenTelemetry are existing code to adapt, not new services. [J1][J2]; local: backend/src/backend/jev.py:221-318, backend/src/backend/extract.py:19-51,301-410, backend/src/backend/compute.py:42-225, backend/src/backend/telemetry.py:43-120.

Evidence challenging or limiting the recommendation

  • The documented standard catalog has no dedicated interactive random games or color wheel. Standard composition may reduce current fidelity; preserving those features may require app-specific A2UI components. [A6][A7]
  • The official CopilotKit example pins 1.73.2 and uses A2UI 0.8, while current source manifests are 1.74.0/A2UI 0.9 and JEV locks CopilotKit 2.0.0-next.1. No official evidence establishes the exact JEV prerelease combination. [C1][C3][C4]; local lock: frontend/package-lock.json:559-654.
  • MAF A2UI is an optional extra with a newer core floor than JEV's current lock. Dynamic progressive rendering is model/client dependent; sample comments warn about Responses/Azure fallback behavior. [M1][M2].
  • Neither the local checkout nor the retrieved primary docs provide an end-to-end latency comparison for JEV-selected versus Luna-authored A2UI. Batching is a qualitative TypeSafe claim, not a time-to-usable-surface measurement. [J1][J5].
  • MAF supports other snapshots/custom events, but the inspected A2UI examples use tool-result/render-tool paths. Do not assume an A2UI custom-event or snapshot integration is already supported by all downstream renderers. [M4][M5].

Confidence, critic, and unresolved gaps

Overall confidence: medium. Direct primary evidence is strong for the protocol and supported tool pathway. Confidence is lower for exact package interoperability and performance because no matching version matrix or app-level benchmark was found.

Final critic: GAPS (active-session result: FAIL). The decision could change if a same-workload proof shows JEV-plus-assembly cannot meet the desired first-frame time, or if JEV's locked CopilotKit preview cannot support the documented A2UI renderer without a version change. The requested research did not include implementation or live model testing, so those gaps remain explicit.

  • Gap 1: no primary-source apples-to-apples time-to-first-usable-surface or action-success result for JEV selection versus Luna-authored A2UI. Next check: the matched temperature-converter proof in the migration section.
  • Gap 2: exact compatibility between the locked CopilotKit 2.0.0-next.1 runtime/core, A2UI renderer, AG-UI JS canary, and MAF A2UI package is not verified. Next check: pin a supported release combination, then run the same proof with the lockfile installed.
  • Gap 3: preserving the rich random and color interactions using only the current standard catalog has not been demonstrated. Next check: make a per-surface scope decision after the standard-catalog proof; do not add custom components before that choice.
